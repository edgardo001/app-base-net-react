## Context

The bug was discovered by clicking the email link in a freshly
created user's mailbox. The link was
`http://localhost:5011/confirm-email?token=…` which served a blank
page because:

- Port 5011 is the backend (`.NET` API), not the React dev server
  (5173).
- The backend has no `GET /confirm-email` route at all — the only
  endpoint is `POST /api/auth/confirm-email`, which expects a JSON
  body and returns 200, not HTML.

The right fix is layered: (a) the backend must emit a link to the
frontend, and (b) the frontend must have a real page at
`/confirm-email` so the link lands somewhere meaningful.

## Architecture compliance

- **Domain**: unchanged. `User.SetEmailConfirmationToken` and
  `User.ConfirmEmail` (which the new page ultimately calls) are
  unchanged.
- **Application**: unchanged. `ConfirmEmailCommandHandler` is
  reused as-is. No new command/query needed for the frontend
  page — it just consumes the existing `POST /api/auth/confirm-email`.
- **Infrastructure**: extends `EmailOptions` with a single
  configuration field. No new repository, no new service, no new
  notification.
- **WebApi**: minimal change. The controller now reads
  `_emailOptions.FrontendBaseUrl` instead of `Request.Scheme` /
  `Request.Host`. This is the same pattern already used for
  `_emailOptions.Templates`.
- **Frontend**: new page, no new dependencies. Uses the existing
  `api` axios instance (so the Vite proxy in dev, and nginx in
  prod, route `/auth/confirm-email` to the backend correctly).

## Why configure the frontend URL instead of detecting it?

A common alternative is "use the `Origin` header of the request
that triggered the email" or "use the `Referer` header". These
both fail for the actual use case: the email is generated by a
server-side request that has no relationship to the user's
browser. The only signal that knows where the user's browser is
pointed is configuration.

`Email:FrontendBaseUrl` is the same pattern used for OAuth
redirect URIs and password-reset links in the rest of the
industry: explicit, env-driven, with a dev default.

## Why a default in `EmailOptions` and not a strict "fail to
start if missing"?

Two reasons:

1. The dev experience. The seeder creates an `admin` user on first
   run, and the dev-only "create user" smoke test emails would
   otherwise be impossible without first setting the env var.
2. The blast radius is loud: a misconfigured frontend URL results
   in broken confirmation links (visible to the user) rather than
   silent data loss. We can tighten this to a startup check later
   if it becomes a recurring problem.

The default `http://localhost:5173` is correct for `dotnet run`
on a developer machine. In production, `Email__FrontendBaseUrl`
or `appsettings.Production.json:Email:FrontendBaseUrl` must be
set to the real origin (e.g. `https://app.example.com`). The
Production appsettings sets it to empty (`""`) to make the
misconfiguration visible: the email link would render as
`/confirm-email?token=…` (no host) which is obviously wrong.

## Frontend page design

- Reads `?token=` from `useSearchParams`.
- On mount, POSTs `{ token }` to `/auth/confirm-email`. Uses
  `useEffect` with a `cancelled` flag to avoid setting state
  after unmount.
- Three UI states:
  - **pending**: spinner + "Confirmando tu correo…"
  - **success**: card title "Correo confirmado" + a primary
    button-styled `<Link to="/login">` "Iniciar sesión"
  - **error**: card title "Enlace inválido o expirado" + the
    API error message (if any) + a secondary
    `<Link to="/login">` "Ir al inicio de sesión"
- If the URL has no `token` query param at all, the page renders
  the error state immediately (no API call).
- Route is registered in `App.tsx` **outside** the
  `<ProtectedRoute>` shell because the user is not yet logged in
  — exactly like `/forgot-password` and `/reset-password`.

## Test coverage

- **Backend** (xUnit): 1 new test, 1 tightened.
  - `CreateUser_SendsEmailWithConfirmationLink` — now asserts the
    body contains the full `http://localhost:5173/confirm-email?token=`
    string (not just the path). Catches regressions where the
    host drifts back to `Request.Host`.
  - `CreateUser_UsesConfiguredFrontendBaseUrl` — creates a
    controller with `EmailOptions.FrontendBaseUrl =
    "https://app.example.com"` and `HttpContext` host =
    `api.example.com`. Asserts the email body contains the
    configured URL and does **not** contain the request host
    (`api.example.com`) or the dev port (`localhost:5011`).
- **Frontend**: no automated test yet (no Vitest infrastructure
  for components in this repo — `AGENTS.md` lists Vitest as
  "future"). Manual verification: `npm run build` succeeds
  (TypeScript clean) and the route appears in `App.tsx`.

## Out of scope

- Migrating `UsersController.CreateUser` to a `CreateUserCommand`
  handler (still controller-orchestrated; the follow-up note in
  `AGENTS.md` points at this).
- Production startup-time validation that `FrontendBaseUrl` is
  set when `ASPNETCORE_ENVIRONMENT=Production`.
- Per-tenant or per-request frontend URLs (white-labelling).
- Multi-language support on the new page (hardcoded Spanish,
  matching the rest of the auth pages).
- A Vitest test for the page itself.
